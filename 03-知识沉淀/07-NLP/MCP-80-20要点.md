# MCP 80/20 要点

> 2026-08-17
> 定位：只记最常用、最常被问的 20%，不展开协议细节。

## 1. MCP 解决什么问题

Agent 要接很多外部工具，每个工具的接入方式都不一样。MCP 用统一标准让 Agent 能发现工具、理解工具、调用工具。

## 2. 三个核心角色

- MCP Server：工具提供方，把真实系统包装成工具
- MCP Client：Agent 这一侧，负责连接 Server
- Tool：一个工具，包含名称、描述、参数

## 3. 发现与调用

```text
Agent → Server：你有什么工具？  （tools/list）
Server → Agent：get_weather，参数 city
Agent → Server：调用 get_weather，city=合肥  （tools/call）
Server → Agent：合肥 26 度，晴
```

## 4. 本地 vs 远程

- 远程 MCP：Server 常驻在服务商服务器，Agent 通过 url 调用
- 本地 MCP：Agent 启动时按 command 拉起进程，会话结束通常停止

## 5. MCP vs API vs Function Calling

- 普通 API：调用方必须写死 URL、参数、鉴权
- Function Calling：模型输出“要调用哪个工具、传什么参数”
- MCP：工具连接和通信的标准协议，让 Agent 能发现和统一调用

## 6. 安全

- 工具白名单
- 参数校验和范围限制
- 敏感操作人工审批
- 沙箱隔离
- 审计日志

## 7. 什么时候不一定需要 MCP

- 只有一个简单工具
- 一次性脚本
- 没有复用和生态需求

这种情况直接 Function Calling 或调 API 更简单。

## 8. 常见面试问题

- MCP 解决什么问题？
- MCP 和 Function Calling 的区别？
- 本地 MCP 和远程 MCP 的区别？
- Agent 怎么发现工具、怎么调用工具？
- 远程 MCP 安全怎么保证？

## 9. 一句话总结

MCP 就是“工具的 USB-C 接口”：让 Agent 不用关心每个工具内部怎么实现，只关心有什么工具、怎么调。

## 10. MCP 的缺点

- 上下文膨胀：工具定义会占用 Token，工具越多越贵
- 认证不统一：不同 MCP Server 的鉴权方式不一致
- 调试复杂：本地进程、JSON-RPC、连接不稳定排查困难
- 工具太多时容易选错：工具选择失败、循环调用
- 安全问题：提示注入、工具投毒、供应链风险、本地任意代码执行
- 不解决 Agent 与 Agent 之间的协作

## 11. 替代 / 补充方案

| 方案 | 定位 |
| --- | --- |
| 直接 API / Function Calling | 简单、少量工具时更轻 |
| CLI / Agent Skills | 本地工具比 MCP 更省 Token、更简单 |
| A2A（Agent2Agent） | Agent 与 Agent 协作，与 MCP 互补 |
| AGNTCY / ACP / OAN | 多 Agent 网络、注册、身份与信任层 |

## 12. 面试结论

MCP 解决“Agent 接工具”的标准问题，但不是万能标准。简单场景用 CLI/Skills，Agent 协作用 A2A，身份信任用 OAN 等基础设施。
